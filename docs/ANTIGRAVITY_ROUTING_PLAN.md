# DevProxy: Antigravity и пять собственных серверов

Дата анализа: 6 октября 2026. Это предложение архитектуры; серверные изменения не выполнялись. Пользователь подтвердил исправность всех пяти маршрутов. Их повторная проверка не является первым этапом ремонта клиента.

Изучены исходники confeden/Antigravity, commit `08b58a5c74289a79d8b9f7a5249f5d94265830c8`, и trustybird/AvenCores-open-antigravity-patcher, commit `b59258fbc2f4c397e3b752c5a9033b5185bd9641`. Сторонние патчеры не запускались. Анализ выполнен самостоятельно, без других моделей и агентов.

## Результат сравнения

| Проект | Что действительно делает | Что полезно для DevProxy |
|---|---|---|
| confeden | Сочетает изменение клиента с loopback CONNECT-прокси, собственным upstream, оценкой маршрутов, чтением служебных журналов и выборочной DNS-маршрутизацией | Раздельное состояние маршрутов, проверка реального результата, сохранение loopback, управление временем ожидания и совместимость с обновлениями |
| AvenCores | Меняет проверки в JavaScript IDE и машинном коде language_server/CLI; отдельно меняет поведение расширения VS Code | Проверка конкретного продукта и архитектуры, отказ при неоднозначной сигнатуре, резервная копия соответствующей версии, явное восстановление |

У confeden часть сетевого механизма отсутствует в публичном дереве: `proxy.rs` условно подключает приватные `relay.rs` и `exits.rs`. Значит, открытый checkout не воспроизводит все маршруты готового авторского выпуска. [Исходник proxy.rs](https://github.com/confeden/Antigravity/blob/08b58a5c74289a79d8b9f7a5249f5d94265830c8/src/proxy.rs).

Важная практика confeden — различать открытый туннель и ответ модели. Непрерывное TLS-соединение не позволяет локальному CONNECT-прокси прочитать отказ Google; проект дополнительно использует журнал language server. Его собственные комментарии описывают, почему неавторизованная проверка API не подтверждает доступ аккаунта. [ls_log.rs](https://github.com/confeden/Antigravity/blob/08b58a5c74289a79d8b9f7a5249f5d94265830c8/src/ls_log.rs), [upstream.rs](https://github.com/confeden/Antigravity/blob/08b58a5c74289a79d8b9f7a5249f5d94265830c8/src/upstream.rs).

AvenCores не является готовым сетевым маршрутизатором для пяти серверов. Его изменения локальных проверок не создают маршрут и не меняют права аккаунта на сервере Google. Windows-запись бинарника в исследованном коде производится на месте с flush/fsync; атомарная замена отдельным файлом реализована для POSIX. Поэтому нельзя переносить обещание атомарности на Windows. [manager/patcher.py](https://github.com/trustybird/AvenCores-open-antigravity-patcher/blob/b59258fbc2f4c397e3b752c5a9033b5185bd9641/source/patcher/manager/patcher.py), [utils/atomic.py](https://github.com/trustybird/AvenCores-open-antigravity-patcher/blob/b59258fbc2f4c397e3b752c5a9033b5185bd9641/source/patcher/utils/atomic.py).

## Лицензии и способ использования

Поэтому прямое включение его кода в наш выпуск без согласия не подходит. [LICENSE confeden](https://github.com/confeden/Antigravity/blob/08b58a5c74289a79d8b9f7a5249f5d94265830c8/LICENSE).

AvenCores распространяется под GPLv3. Копирование существенных частей в объединённый распространяемый продукт требует соблюдения GPL; его нельзя просто переобозначить MIT. Отдельный самостоятельный инструмент может оставаться отдельной программой, но это зависит от характера интеграции, а не от наличия отдельного процесса. Предлагаю самостоятельно реализовать сетевые механизмы по стандартным протоколам, без переноса патчерного кода. [LICENSE AvenCores](https://github.com/trustybird/AvenCores-open-antigravity-patcher/blob/b59258fbc2f4c397e3b752c5a9033b5185bd9641/LICENSE), [пояснения FSF об объединённых и отдельных программах](https://www.gnu.org/licenses/gpl-faq.en.html#MereAggregation).

## Роли вашей инфраструктуры

| Сервер | Предлагаемая роль |
|---|---|
| Финляндия | Кандидат основного выхода; выбрать после замеров |
| Италия | Второй кандидат основного выхода и резерв |
| Исландия | Независимый резерв, если подтверждена работа нужных сервисов |
| США | Дополнительный выход и резерв; задержку измерить |
| Россия | Необязательная входная точка для цепочки до зарубежного выхода; не выбирать автоматически конечным выходом для Google |

Четыре зарубежные страны присутствуют в официальном списке доступности Antigravity; Россия в этом списке отсутствует. Это не гарантирует доступ с любого IP дата-центра или для любого аккаунта. Google отдельно указывает на связанный с аккаунтом регион. [Официальный FAQ](https://www.antigravity.google/docs/faq/).

Основной путь: Antigravity и выделенный браузер входа → локальный агент DevProxy → один собственный зарубежный HTTPS CONNECT-прокси → Google. При необходимости: агент → разрешённая российская входная точка → тот же зарубежный выход → Google. Российский вход должен быть реально доступен из вашей сети; собственный сервер не заставляет внешний прокси разрешить запрещённый адрес. Цепочка добавляет задержку и точку отказа, поэтому прямой зарубежный маршрут предпочтителен, если доступен.

Существующий HTTP CONNECT можно оставить для первого проверочного этапа через защищённый канал Amnezia. Для самостоятельной работы DevProxy без включённого VPN предлагается HTTPS CONNECT с проверкой серверного сертификата и индивидуальными учётными данными. Транспорт ПК → прокси должен быть защищён; TLS между приложением и Google остаётся непрерывным. Собственный CA и расшифровка трафика Google не требуются. mTLS можно добавить позже как отдельную возможность профиля.

## Изменения в DevProxy по приоритету

1. **Диагностика Antigravity по этапам.** Раздельно показывать: агент/порт, доступ к upstream, авторизация прокси, TLS к нужному сервису, вход в аккаунт, получение моделей, начало ответа. Статус «работает» требует актуального подтверждения ответа, а не только запуска EXE. Сохранять только время, имя хоста, тип ошибки и маршрут; не сохранять URL с параметрами, токены, промпты или ответы.

2. **Вход через тот же маршрут.** Существующий браузер по умолчанию может работать вне настроек запущенной IDE. Нужен выделенный экземпляр внешнего браузера с собственным профилем и явно заданным локальным прокси. Браузер входа и language server должны использовать один выбранный выход в течение входа. Loopback-страницы и callback остаются локальными. Конкретный способ передачи OAuth URL нужно проверить на установленной версии; глобально менять браузер по умолчанию не следует.

3. **Проверка language server отдельно от Electron.** Проверять происхождение процесса, его выбранную конфигурацию прокси и фактическое подключение. Стандартные HTTP_PROXY/HTTPS_PROXY и loopback NO_PROXY уже формирует launcher DevProxy; это не доказывает, что любой компонент их соблюдает. Go и gRPC C-Core имеют разные правила выбора прокси, а приложение может использовать собственный транспорт. [Go httpproxy](https://pkg.go.dev/golang.org/x/net/http/httpproxy), [gRPC C-Core proxy mapper](https://grpc.github.io/grpc/core/md_doc_core_default_http_proxy_mapper.html).

4. **Группа из четырёх зарубежных профилей.** Добавить выбор «Авто» и закрепление конкретного сервера. Сначала проверять пригодность маршрута, затем учитывать стабильность и задержку. Сохранять выбранный выход для текущей сессии; не распределять каждый запрос случайно по странам. Российский вход включается отдельным параметром и не превращается в пятый равноправный выход.

5. **Безопасное переключение.** До подтверждения CONNECT клиенту можно попробовать другой разрешённый маршрут при транспортном сбое. После передачи данных соединение нельзя незаметно продолжить на другом сервере: оно должно завершиться ошибкой, а новый запрос может получить другой маршрут. Не повторять автоматически уже отправленную генерацию или действие агента. Недоступные выходы временно исключать с увеличением интервала повторной проверки. Если все выходы недоступны, локальный туннель остаётся без прямого fallback; это ещё не гарантирует блокировку обхода со стороны самого приложения.

6. **Белые списки назначений.** Отдельно проверять доступ ПК к адресам прокси и разрешённые назначения на самих прокси. Начальный каталог содержит accounts.google.com, oauth2.googleapis.com, cloudcode-pa.googleapis.com и daily-cloudcode-pa.googleapis.com; дополнительные хосты загрузок и интерфейса добавляются по наблюдаемому сценарию и с указанием причины. В локальных журналах также встречаются generativelanguage.googleapis.com, storage.googleapis.com, www.googleapis.com, www.gstatic.com, lh3.googleusercontent.com и play.googleapis.com. Это наблюдения, а не полный нормативный список. Диагностические запросы к GitHub/Cloudflare не должны быть условием запуска.

7. **Управление серверными конфигурациями.** Согласованный каталог разрешённых host:port, закрытый доступ к приватным/служебным адресам со стороны выходного прокси, индивидуальная авторизация, ограничения соединений, отзыв ключей и журнал технических отказов. Политики должны проверять также результат DNS-разрешения, а не только переданное имя. Не включать общие секреты инфраструктуры в публичный EXE. Для обычного CONNECT возможны правила по хосту и порту; содержимое HTTPS и API-ошибки он не видит.

## Что не включать в базовый режим

Не подменять признаки eligibility/auth как основной способ сетевого ремонта: открывшийся интерфейс не означает работающий аккаунт. Не отключать TLS verification, не закреплять один сторонний DNS-провайдер и не замораживать обновления приложения постоянно. Не стирать профиль для «обнуления квоты»: переавторизация может исправить состояние клиента, но серверная квота от этого не становится гарантированно новой.

NRPT — правило разрешения имён для namespace Windows, а не фильтр конкретного процесса. Оно может затронуть другие приложения, обращающиеся к тем же именам. При наличии собственных CONNECT-выходов этот механизм не нужен в первом этапе. Полный перехват выбранных процессов через WFP — отдельная работа с привилегированным компонентом; текущая версия DevProxy этого не обеспечивает. [Microsoft NRPT](https://learn.microsoft.com/en-us/powershell/module/dnsclient/add-dnsclientnrptrule?view=windowsserver2025-ps).

## Проверяемые критерии готовности

- При выключенном VPN вход, загрузка моделей и реальный ответ работают через один выбранный собственный выход.
- Подтверждён маршрут language server, а не только Electron; внутренний интерфейс и OAuth callback не покидают loopback.
- Запрещённый прокси хост, HTTP 407 прокси, ошибка TLS, региональный отказ Google, недостаточные права аккаунта и лимит запросов показаны как разные причины.
- Подтверждён транспорт HTTP/2/SSE внутри CONNECT, долгие ответы и корректное закрытие соединений.
- Отключение одного сервера не создаёт прямой маршрут и не повторяет уже отправленное действие.
- Недоступность GitHub/Cloudflare не блокирует запуск; список разрешённых назначений проверяется на реальном сценарии.
- Смена версии Antigravity не приводит к слепой записи в её файлы; резервная копия и откат соответствуют конкретной версии и хешу, если отдельный совместимый патч вообще будет выбран.

## Что удалось подтвердить локально

Установленный language_server.exe содержит стандартные литералы HTTPS_PROXY/https_proxy и не содержит AG_LS_PROXY. Установленная Electron-оболочка объявляет версию пакета 2.11.0.

После уточнения пользователя проверен действующий клиент: language_server имеет четыре TCP-соединения к локальному мосту DevProxy и не имеет прямых внешних соединений в наблюдённом снимке. Поэтому версия «прокси применяется только к Electron» не подтверждается. Журнал language_server содержит ошибки открытия HTTPS-запросов Bad Gateway.

Адресный тест одного назначения daily-cloudcode-pa.googleapis.com дал HTTP 502 на действующем мосту 127.0.0.1:65370. Новый изолированный мост из текущих исходников с сохранённым выбранным профилем «Прокси 2» открыл CONNECT к тому же назначению с HTTP 200. Сообщения и авторизованные запросы модели в тесте не отправлялись. Это локализует проблему в действующей сессии/её сохранённых в памяти параметрах или установленной сборке DevProxy; пока не установлено, какая из этих причин точная. Успешный CONNECT не подтверждает ответ модели или права аккаунта.

Первый практический этап теперь — показать точную ошибку действующего туннеля, сопоставить его профиль с актуальным сохранённым профилем и безопасно обновить сессию. Проектирование выбора пяти выходов остаётся дальнейшим улучшением, а не объяснением текущего отказа.
